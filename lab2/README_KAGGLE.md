# ЛР2: выполнение подготовленных заданий в Kaggle

## Что уже подготовлено

- 90 рабочих утверждений SciFact; holdout из 210 утверждений не используется.
- BGE-small-en-v1.5 на CPU: матрица 5183 × 384, нормализация L2, предел 512 токенов.
- Входы для пяти серий: llm_only 90, rag_k3 90, oracle 60, rag_k1 90, rag_k5 90.
- Весь вход модели, включая шаблон диалога, не превышает 2048 токенов.
- Температура 0; ответ не более 128 токенов; статическая JSON Schema через response_format.

Архив входов: `lab2_inputs_95219452.zip`.

SHA-256: `c094a4dd19f02b92c501871b68fc9574668bcc596775852aa200daf0e1304139`.

Коммит подготовки: `66e7009a009ed1f7383cbdfd206e153c7a38d5e8`.

Коммит запуска будет новым: он добавляет клиент, управление сервером и блокнот.
В метаданных результатов сохраняются оба коммита. Исходники подготовки проверяются
по снимкам из входного архива с учётом преобразования CRLF/LF Windows → Linux.

## 1. Проверка на ноутбуке

Команды выполняются из корня intsys-labs:

```powershell
& ".\.venv\Scripts\python.exe" ".\lab2\verify_runtime.py" `
    --inputs ".\runs\lab2_prepare\95219452bef84676a0932e060d22b893"
```

Ожидаются шесть успешно пройденных тестов. Они проверяют:
целостность входов; блокировку при несовпадении токенов; пять режимов и 420 записей;
отсутствие повторных вызовов завершённых серий; продолжение с сохранением неудачной попытки;
запрет смешивания изменившихся условий. Фиктивные результаты остаются во временной папке
и не используются как результаты эксперимента.

## 3. Подготовка Kaggle

1. Импортируй `lab2/lab2_kaggle.ipynb` как новый ноутбук Kaggle.
2. Создай приватный Dataset из `lab2_inputs_95219452.zip` и подключи его к ноутбуку.
   Можно использовать ZIP либо его автоматически распакованное Kaggle содержимое:
   блокнот распознаёт оба варианта и сверяет хеши.
3. Включи Internet для GitHub, пакетов и Hugging Face.
4. Выбери GPU T4. При выделении T4 ×2 код использует только первую карту.
5. В первой ячейке вставь полный хеш нового коммита запуска.

В ядро блокнота вычислительные библиотеки не импортируются. В отдельном окружении
`/tmp/lab2-env` используется Python 3.13, vLLM 0.33.0 и совместимый PyTorch.
Рецепт установки повторяет успешный вариант ЛР1: uv с `--torch-backend=auto`.
Точные установленные версии сохраняются в `requirements_gpu.txt`.
Отдельный процесс проверяет доступность одной T4 и выполнение CUDA-операции.

## 4. Сервер и проверки

Сервер: Qwen/Qwen3-4B-Instruct-2507,
ревизия `cdbee75f17c01a7cc42f958dc650907174af0554`, FP16,
контекст 32768, max_num_seqs=32, max_num_batched_tokens=2048,
gpu_memory_utilization=0.9, tensor_parallel_size=1, TRITON_ATTN,
generation-config=vllm, кеширование префикса выключено.
Все основные вызовы идут последовательно, по одному.

Проверка `check` сначала обращается к `/tokenize`: 420 основных входов и два входа прогрева.
Это подсчёт токенов, а не генерация ответов. Затем выполняются два пробных вызова на claims_train.
Для каждого ответа usage.prompt_tokens должен совпадать с локально подготовленным числом.
Расхождение блокирует запуск основной серии; скрытая обрезка входа не применяется.

В запросах используются temperature=0, top_p=1, seed=0, max_tokens=128,
top_k=-1, repetition_penalty=1, presence_penalty=0, frequency_penalty=0,
ignore_eos=false, stream=false и response_format с сохранённой JSON Schema.

## 5. Эксперименты

В эксперименте 1 по очереди запускаются llm_only, rag_k3, oracle — 240 основных вызовов.
Затем создаётся промежуточный ZIP. В эксперименте 2 выполняются rag_k1 и rag_k5 — ещё 180 вызовов.
Для каждого режима есть отдельный процесс, run_id и папка runs/<run_id>.
Прогревочные вызовы сохраняются отдельно и не входят в 420 основных записей.
Oracle использует такой же документный шаблон, поэтому прогревается сохранённым документным
запросом из claims_train; оценка oracle проводится только на его 60 основных заданиях.

Поиск и сборка контекста выполнены на ноутбуке. Поле search_s сохранено из этой подготовки
один раз на утверждение и переиспользуется для трёх k. Это не повторное измерение онлайн-поиска.
generation_s измеряет клиентское время от отправки HTTP-запроса до получения полного тела ответа;
загрузка модели, запись файлов и разбор JSON в него не входят.

## 6. Сохранение и продолжение

Каждая запись results.jsonl содержит исходный task_id и claim_id, режим и k,
найденные и переданные документы, сообщения и промпт, число токенов,
сырой текст ответа и тело HTTP-ответа, usage, статус разбора, время и ошибки.
Результат записывается и сбрасывается на диск после каждого вызова.
Неудачные ответы не удаляются и автоматически не запрашиваются повторно.

Повтор той же ячейки продолжает только отсутствующие записи. Завершённый режим проверяется
по хешу результатов и пропускается. При изменении кода, входов или профиля сервера
автоматическое продолжение блокируется. При остановке контроллер пытается аккуратно
завершить текущую попытку и создаёт промежуточный архив. Если JSONL оказался оборван посередине
строки, проверка остановится: такой файл автоматически не исправляется и не удаляется.

Запуски фиксируют физическую GPU и версии. После перезапуска сервера требуется новый check;
продолжить прежний основной режим можно только при неизменном профиле оборудования и библиотек.

## 7. Что скачать

Итоговый ZIP и .sha256 появятся в `/kaggle/working` и будут доступны в панели Output.
Скачай их и сохрани выполненный IPYNB с выводом. После скачивания заверши GPU-сессию Kaggle.
Остановка процесса модели не отключает выделенный ускоритель.

В архиве находятся входы, ответы, конфигурации, паспорта, журналы, зависимости и исходники.
Accuracy ещё не вычислена: эталонные метки остаются для локального этапа оценки.
Матрица индекса хранится на ноутбуке и будет добавлена в итоговый архив артефактов ЛР2.
Следующий шаг — локальный анализ, попарные сравнения, регистрация в MLflow и отчёт.
