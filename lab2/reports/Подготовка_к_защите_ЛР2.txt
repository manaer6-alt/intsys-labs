РАССКАЗ НА 1–2 МИНУТЫ

В этой работе я проверял, помогает ли языковой модели поиск научных свидетельств.
Я использовал SciFact: корпус из 5183 аннотаций и утверждения с тремя метками:
SUPPORT — есть размеченное обоснование за утверждение, CONTRADICT — против,
NOINFO — размеченного обоснования нет.

По правилу методички выделил 90 утверждений, по 30 каждого класса. Ещё 210
отложил для следующей работы. На CPU построил векторный индекс BGE-small:
каждую аннотацию представил вектором из 384 чисел. Для утверждения вычислял
его вектор и находил наиболее близкие документы. Затем собирал контекст
из целых предложений в пределах 2048 токенов модели Qwen.

На Kaggle использовал одну T4 и готовую Qwen3-4B-Instruct-2507 через vLLM.
Модель не обучал. Сравнил ответы без поиска, с тремя найденными документами
и с эталонным свидетельством — это диагностический режим oracle.
Затем повторил RAG с одним и пятью документами. Всего получил 420 основных ответов.

Без поиска точность составила 41,11%, с тремя документами — 77,78%.
RAG исправил 37 ошибок и испортил 4 ранее верных ответа. С одним документом
точность оказалась 78,89%, с пятью — 74,44%. Больше найденных свидетельств
не гарантировало лучшего ответа.

У oracle выявил ошибки ссылок: 26 ответов ссылались на непереданные номера
предложений. По исходным правилам точность составила 26 из 60; отдельно
50 из 60 меток совпали с эталоном. Эти показатели я не смешивал.
После уменьшения бюджета до 1024 токенов число полностью переданных обоснований
снизилось с 51 до 48 из 60 без новых вызовов Qwen. Главный вывод: отдельно
проверять поиск, переданный контекст, метку и ссылку.


КАК РАБОТАЕТ СИСТЕМА — ПРОСТЫМИ СЛОВАМИ

1. Исходные данные находятся на локальном компьютере. BGE один раз кодирует
   все аннотации. Индекс — обычная матрица, отдельной векторной базы нет.
2. Для каждого из 90 утверждений BGE вычисляет вектор. Скалярное произведение
   с нормированными векторами корпуса даёт оценки близости и первые 5 документов.
3. Python собирает английские инструкции, утверждение, документы и исходные
   номера предложений. В 2048 входит весь промпт с шаблоном диалога.
4. Подготовленные промпты, конфигурации и контрольные суммы передаются в Kaggle.
   Там клиент отправляет текст серверу vLLM через HTTP API. Поиск уже выполнен;
   сам сервер vLLM не ищет документы SciFact.
5. Сервер токенизирует текст и выполняет готовую Qwen на GPU. Ответ ограничен
   JSON Schema и 128 выходными токенами. 128 — верхний предел, не обязательная длина.
6. Клиент сохраняет полный запрос, сырой ответ, usage, время и результат проверки.
7. Локально модуль оценки читает эталон, пересчитывает метрики и создаёт таблицы.
   MLflow хранит уже полученные результаты. При импорте модель повторно не вызывается.


ОСНОВНЫЕ ТЕРМИНЫ

RAG — retrieval-augmented generation, генерация, дополненная поиском.
LLM — large language model, большая языковая модель; здесь Qwen.
Encoder, кодировщик — модель, которая превращает текст в вектор; здесь BGE.
Embedding, эмбеддинг — числовое представление текста, здесь 384 числа.
L2-нормализация — деление вектора на его длину, после чего длина равна 1.
Косинусная близость — мера направления векторов. Для L2-нормированных векторов
равна скалярному произведению. Это не вероятность истинности утверждения.
Top-k — первые k документов в ранжированном списке; k не число токенов.
Rationale — эталонное обоснование: набор предложений одного документа.
Prompt, промпт — весь вход модели: инструкции, утверждение, контекст и шаблон диалога.
Токен — единица кодирования текста. Токенизаторы BGE и Qwen различаются.
Oracle — диагностика с заранее известным эталонным обоснованием вместо поиска.
Это не самостоятельная система для неизвестных утверждений: она использует разметку.
JSON — формат структурированных данных. JSONL — по одному JSON-объекту на строку.
JSON Schema — правила полей и типов ответа; не проверяет научную истинность.
Accuracy — доля верных ответов; в нашем протоколе требуется ещё успешная валидация.
Recall класса — доля верно распознанных примеров данного истинного класса.
Hit@k — найден ли хотя бы один эталонный документ среди первых k.
Recall@k — доля всех эталонных документов, найденных среди первых k.
RR@k — 1 / ранг первого эталонного документа; 0, если он не найден в top-k.
MRR@k — среднее RR@k по оцениваемым утверждениям.
Доля переданного обоснования — доля примеров, для которых в промпте целиком
есть хотя бы одно альтернативное эталонное обоснование одного документа.
Верная ссылка — верная метка плюс ссылка, содержащая полное эталонное обоснование.
SHA-256 — контрольная сумма байтов. Она обнаруживает изменение файла;
это не шифрование и не способ оценить качество ответа.
Манифест — паспорт происхождения, состава, разбиения и контрольных сумм данных.
Ревизия модели — конкретная версия файлов в репозитории Hugging Face.
run_id — идентификатор отдельного запуска; исходный ID и ID MLflow различаются.


СЕМЬ ВОПРОСОВ МЕТОДИЧКИ

1. Модель ответила NOINFO на SUPPORT. Где потерялось свидетельство?

   Смотрим три вещи: top-k, реально переданные предложения и наличие полного
   эталонного обоснования. Нет нужного документа в top-k — ошибка поиска.
   Документ найден, но обоснование не вошло — ошибка сборки/бюджета.
   Полное обоснование передано, метка неверна — ошибка ответа модели.
   Наш пример ID 70: ответ NOINFO, эталон SUPPORT. Документы 5956380 и 4414547
   отсутствуют даже в top-5. Источник проблемы — поиск.

2. Два релевантных документа, один найден третьим. Какие метрики?

   При k=3: Hit=1, Recall=1/2=0,5, RR=1/3. При k=1 все равны нулю.
   Hit не равен Recall: попадание одного документа не означает, что найдены все.

3. Чем обрезка кодировщика отличается от бюджета контекста?

   BGE при построении вектора видит максимум 512 своих токенов. Так обрезаны
   455/5183 аннотации, то есть 8,78%; это записано в passport.json.
   Исходная аннотация не укорачивается. Затем сборщик отдельно укладывает
   предложения в 2048 токенов Qwen вместе с инструкциями и шаблоном.
   В results.jsonl сохранены found, passed, prompt, prompt_tokens.
   По ним видно, что найдено и что фактически получила языковая модель.

4. Почему при k=5 Recall вырос, а у части примеров промпт может не измениться?

   Выдачи вложенные: top-3 входит в top-5. Дополнительный документ способен
   увеличить Recall поиска. Однако если бюджет заполнен первыми документами,
   новые не попадут в промпт. Проверять нужно полный prompt и passed.
   В нашей серии полные промпты k=3 и k=5 совпали для 6 из 90 ID:
   130, 143, 521, 535, 971, 1298. Например, ID 130: при обоих k переданы только
   27768226:[0–41] и 16979690:[0–12]; бюджет исчерпан на первых документах.
   Общая доля переданного обоснования всё же выросла с 51/60 до 53/60.

5. Метка верна, а ссылка не содержит обоснования. Как учтён ответ?

   Если документ и номера действительно передавались, формат проходит проверку:
   Accuracy засчитает верную метку, доля верных ссылок — нет.
   Если номер вообще не передавался, валидатор отклонит ответ, поэтому
   в нашем исходном протоколе он неверен и для Accuracy.
   У oracle: 26/60 верных по основной метрике, но только 24/60 полных верных ссылок.
   Диагностика одной метки на всех 60 даёт 50/60; это отдельный показатель.

6. Почему нельзя сравнить oracle на 60 с общей RAG Accuracy на 90?

   Состав задач различается: у oracle нет NOINFO. Для корректного сравнения
   берём те же 60 SUPPORT/CONTRADICT во всех режимах:
   LLM-only 20/60=33,33%; RAG k=3 51/60=85%; oracle 26/60=43,33%.
   Даже диагностическая точность меток oracle 50/60 ниже RAG на один пример.

7. Что произойдёт при бюджете 1024? Можно проверить без новой генерации?

   По нашему алгоритму контекст — начальная часть списка целых предложений.
   Уменьшение бюджета может сохранить или уменьшить покрытие обоснований.
   Мы повторили упаковку тех же документов и подсчёт токенов, затем проверили
   наличие полного эталонного обоснования: 51/60=85% -> 48/60=80%, минус 5 п.п.
   Потеряли полное обоснование ID 185, 513, 1121. Новые ответы Qwen не получали.
   Новая Accuracy при бюджете 1024 неизвестна.


ДОПОЛНИТЕЛЬНЫЕ ВОПРОСЫ

Почему не взяли все 300 утверждений для экспериментов?
— Методичка фиксирует 90 для разработки, 210 оставляет для независимой проверки
  следующей работы. Разбиение сделано до генерации по хешам внутри каждого класса.

Где обучение?
— В этой работе его нет. BGE и Qwen уже обучены. Мы строим индекс и выполняем
  инференс — применение готовой модели, затем оцениваем ответы.

Что связывает работу с ЛР0 и ЛР1?
— Из ЛР0: воспроизводимость, манифест, Git, конфигурации, ID запусков, MLflow.
  Из ЛР1: та же модель и подход к развёртыванию API-сервера vLLM на одной T4.

Что означает 2048?
— Верхний предел всех входных токенов Qwen после chat template: инструкции,
  утверждение, заголовки, номера предложений и тексты. Это не 2048 слов и не
  предел самого сервера: сервер настроен на контекст 32768 токенов.

Как исключили утечку разметки?
— Поиск и обычная сборка контекста работают по тексту утверждения и корпусу.
  Эталон читает оценка. Только oracle специально получает одно эталонное
  обоснование — этот режим явно диагностический. Предсказанная метка ему не сообщается.

Зачем английские промпты?
— Методичка требует английский язык инструкций, как и у SciFact. В BGE к запросу
  добавлена рекомендованная английская инструкция поиска релевантных фрагментов.

Почему JSON Schema не предотвратила 26 ошибок oracle?
— Она задаёт типы и допустимые метки. Список sentences содержит целые числа,
  но статическая схема не знает, какие номера вошли в конкретный промпт.
  Проверка принадлежности выполняется отдельным валидатором после ответа.

Что было с номерами oracle?
— Во всех 26 случаях JSON синтаксически допустим, но содержит непереданные номера.
  В 24 случаях множество номеров равно переданному множеству минус один.
  Это наблюдаемый шаблон, а не доказанная внутренняя причина поведения модели.
  В примере ID 56 передано [1], модель вернула [0,1], поэтому ответ отклонён.
  Номера после эксперимента не исправляли, неудачные ответы не исключали.

Почему k=1 лучше k=3, хотя поиск слабее?
— Разные показатели измеряют разные этапы. При k=3 больше эталонных источников
  найдено и передано, но модель чаще ошибается на NOINFO: 11 против 6 ошибок.
  На SUPPORT/CONTRADICT k=3 лучше: 51 против 47 верных ответов.
  Итоговое преимущество k=1 — только 1/90=1,11 п.п.; это не доказательство
  универсального превосходства одного документа.

Что значит «исправлено 37, испорчено 4»?
— Сопоставили ответы на одинаковые ID. У 37 LLM-only был неверен, RAG верен;
  у 4 — наоборот. Чистый прирост 33/90=36,67 п.п. Это не 37 дополнительных
  правильных ответов в суммарной точности: из них нужно вычесть четыре ухудшения.

Достаточно ли правильной метки для доказательства, что RAG использовал источник?
— Нет. Есть 7 положительных примеров k=3 с верной меткой без найденного
  размеченного документа. Даже совпадение ссылки с разметкой не доказывает
  внутренний ход рассуждения. Мы оцениваем наблюдаемые ответы и ссылки.

Можно ли складывать предложения разных эталонных обоснований?
— Нет. Должен целиком войти хотя бы один альтернативный список sentences
  одного документа. Части разных альтернатив не образуют автоматически полное обоснование.

Что измеряет generation_s?
— Время клиентского HTTP-вызова до получения полного тела ответа. Включает
  сервер, генерацию и обмен, но не заранее выполненный поиск. Это не TTFT,
  не TPOT и не чистое время арифметических операций GPU.

Какие необязательные улучшения уже выполнены?
— Другой encoder, перевод запросов и отключение response_format не исследовались.
  Пересчёт бюджета 1024 выполнен для вопроса защиты, без новой генерации.
